Dynamic Programming

Quick reference · C++ · sources: CPH ch. 7, USACO Guide: Intro to DP

Spot it

  • “Maximum / minimum / number of ways”, and every choice affects which choices are left later (CPH: “finding an optimal solution” or “counting the number of solutions”)
  • A brute-force recursion is easy to write, but the same arguments come up again along different paths
  • Constraints too big for 2n, but small enough for (number of states) × (choices per state)
  • Examples: 198, 213, 322 (CPH’s coin problem), 337 (on a tree)
  • On a tree: the parent’s choice depends on a fact about the child (was it robbed?), not only on its best value

The recipe

Write the brute force as a recursion whose answer depends only on its arguments. Then store each answer the first time it is computed. (Lesson 7)
  1. Contract: f(state) = the answer for that part of the problem only.
  2. Choices: what can you do at this state? Each choice gives a smaller state. Combine them with max, min or +.
  3. Base cases: the states with an obvious answer, checked before any recursion.
  4. Memo: an array indexed by the state, a lookup before the work, and a store after it.
  5. Cost ≈ (number of states) × (work per state).
  6. Optional: tabulate. Loop in the order that fills each state’s inputs first.
std::vector<int> memo;              // memo[s] == -1: not computed yet

    if (memo[s] != -1) return memo[s];

DP on a tree

If the parent needs more than one fact about a child, the child returns more than one value. Each node is then called once, by its parent: O(n), with no memo. (Lesson 8; CPH §14.2 keeps two values per node for the diameter.)
  • The “skip a level” recursion (f of the grandchildren) asks about every node twice. On a vine it is 198’s plain recursion.
  • If you do memoise on a tree, key by TreeNode*, never by val: values repeat, subtrees don’t.

Pitfalls

BugSymptom
no memocorrect, but exponential: small cases pass, then it never finishes (198: about 1021 calls at n = 100)
sentinel 0 when 0 is a real answerthe memo never hits on those states, so an all-zero input is exponential again
the answer depends on something other than the arguments (a global that changes, a running total)stored answers are wrong when they are reused; put it in the state, or return it
memo lookup before the base casememo[n] is read out of bounds: an assertion or ASan crash before the first case finishes
lookup, but no storethe memo never hits, so the code is still exponential (198: correct, then “still running after 2 s”)
memo keyed by a value that doesn’t determine the answer (337: t->val)wrong answers wherever two states share the key
passing the input vector by valuea copy per call: O(n) extra work per call
loop in the wrong directionreads entries that aren’t filled yet (still 0 or −1)

Template (LC 198)

Two correct states. Both pass 20/20 (./test.sh 198), and both were stress-tested on 200,000 random streets.

// A: best(i) = most money from houses i..n-1 (the lesson's). Skip or rob covers every plan.
int rob(std::vector<int>& nums) {
    int n = nums.size();
    std::vector<int> best(n + 2, 0);              // best[n] = best[n+1] = 0: no houses left
    for (int i = n - 1; i >= 0; i--)              // reads i+1, i+2: fill right to left
        best[i] = std::max(best[i + 1], nums[i] + best[i + 2]);
    return best[0];
}
// B: best[i] = most money from houses i..n-1 GIVEN house i is robbed (the learner's, cold).
// The next robbed house is i+2 or i+3, never i+4+: adding i+2 stays legal and,
// since nums >= 0, can't lower the total. Breaks on negatives: [5,-1,-1,-1,5].
best[i] = nums[i] + max(best[i+2], best[i+3]);   answer = max(best[0], best[1])
