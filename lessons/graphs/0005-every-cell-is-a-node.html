Every Cell Is a Node

LC 200 Number of Islands: a grid is a graph you never build, and searching it needs one thing 301 never did

Your win today: count the islands in a 300×300 grid by visiting each cell once. That’s your first graph search, and it’s the core of most “grid” Mediums.

1. The grid is a graph

A graph is just nodes plus edges between them (CPH ch. 11). In LC 200:

  • node: a land cell (r, c)
  • edge: two land cells that touch up, down, left or right. Diagonals don’t count.
  • island: a connected component, meaning every land cell you can reach from a starting cell

As in Lesson 2, you never build the graph. You work out a cell’s neighbours as you need them:

const int dr[] = {1, -1, 0, 0}, dc[] = {0, 0, 1, -1};   // down, up, right, left
for (int d = 0; d < 4; d++) { int nr = r + dr[d], nc = c + dc[d]; /* ... */ }

So counting islands means counting connected components. A depth-first search from one node reaches exactly its own component (CPH §12.3, “Connectivity check”). The algorithm is a scan and a fill:

Scan every cell. When you find land that isn’t marked yet, it’s a new island: count it, then fill it by DFS, marking everything the fill reaches. When the scan later reaches those cells, it skips them because they’re already marked.
USACO calls the fill step flood fill: “an algorithm that identifies and labels the connected component that a particular cell belongs to” (USACO Guide).

2. The one new thing: you can walk in circles

In 301’s tree, every call moved to i + 1, so a call could never lead back to itself. A grid has no such direction. (0,0) has (0,1) as a neighbour, and (0,1) has (0,0) as a neighbour, so an unguarded DFS goes back and forth forever.

The rule: mark a cell the moment you arrive, before trying any neighbour. Every call checks the mark first and returns at once if the cell is already marked. This is how CPH writes it (§12.1): if (visited[s]) return; visited[s] = true;.

You can mark in either of two ways: keep a separate visited array, or overwrite the land with '0' (“sink” it). Both are fine for LC 200.

3. See it

Step through the scan and fill. The dashed outline is the scan, the red outline is the running fill call, and marked cells show their island number. Then untick “mark a cell on arrival” and step again: watch the call stack keep growing.

With marking on, each cell is entered once and checked at most four more times, once from each neighbour. That makes it O(mn). It’s CPH’s O(n+m) for DFS, with mn nodes and at most 2mn edges.

4. Check yourself

1. When must the fill mark cell (r, c)?

If you mark later, a neighbour can call back into (r, c) while it’s still unmarked, and the two cells keep calling each other until the stack overflows. You just watched this happen in §3.

2. 301’s DFS was exponential. What is this one on an m×n grid?

301 searched paths (sequences of choices), and there are exponentially many. This search visits nodes, and the mark ensures each node is expanded only once. Marking is what turns “every path” into “every cell once”.

3. In 111/101/111, why is the ring counted once, not twice?

The count goes up only in the scan, and only on unmarked land. The first fill goes all the way round the ring, so by the time the scan gets past (0,0), every ring cell is marked.

Hint 1

The fill does three jobs, in this order: reject (off the grid, water, or already marked), mark, recurse into the four neighbours. It returns nothing; marking is its only effect.

Hint 2

Check that r and c are on the grid before you read grid[r][c]. Otherwise ASan reports a heap-buffer-overflow.

Hint 3

The counter belongs to the scan only, just as the , belonged only to the parent in 1106. The fill never counts anything.
