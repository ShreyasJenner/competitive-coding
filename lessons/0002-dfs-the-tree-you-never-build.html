The Tree You Never Build

Depth-first search as recursion over choices, the missing step in LC 301

Your win today: a ten-line DFS that lists every subsequence of a string. Once it works, step 2 of 301 is that same function with three ifs added.

1. You’ve already written one

Here’s your count_descendants from LC 230:

int count_descendants(TreeNode *ptr) {
  if (ptr == NULL) return 0;                    // base case
  int leftcount  = count_descendants(ptr->left);  // go all the way down the left first
  int rightcount = count_descendants(ptr->right); // only then try the right
  return leftcount + rightcount + ...;
}

That is a depth-first search (DFS). Each call dives all the way down one branch before it comes back to try the next. In 230 the tree already exists in memory, built from TreeNode pointers. In 301 there is no tree in memory. The tree from Lesson 1 exists only as the pattern of function calls:

Its children are…ptr->left, ptr->rightthe recursive calls it makes, one per choice about s[i]

Resultreturned and summedat a leaf, path is pushed into an output list
Laaksonen’s Handbook §5.1 builds subsets with exactly this search(k) recursion: for each element, one call without it and one call with it.

2. Watch it run

This DFS lists every subsequence of s, meaning every string you can get by deleting any characters. It’s Lesson 1’s keep/delete tree without any pruning. Step through it and keep an eye on the call stack and on path, especially at line 9.

(up to 4 characters; click the box below, then use ← → keys)

Line 9 is the “back” in backtracking. Every call must hand path back to its caller exactly as it received it. The keep branch appends a character, so it must remove it again before returning. Otherwise the caller’s next choice starts from a corrupted path.

3. Predict

Without the stepper, write the order in which leaves are recorded for s = "abc". Type letters only, and _ for the empty string.

Delete comes first, so the leftmost path deletes everything: "". Then the deepest undecided character (c) flips to “keep”. Only after every combination of b,c is done does a flip. It works like counting in binary, with a as the slowest digit.

4. Check yourself

1. In 230 a node’s children were ptr->left/ptr->right. Here, what are a node’s children?

Nothing is stored. A child exists only while its call is on the stack. (The last option describes a different tree for 301, the one a BFS would search.)

2. Why does line 9 call path.pop_back()?

Choose, explore, un-choose. path is shared by every call, so each call must undo its own edit.

3. For a string of length n, how many leaves does this DFS reach?

There are two choices per character and n characters, so 2·2·…·2 = 2n. That’s why 301’s pruning matters.

4. In 301 the budget changes per branch. Where should rmL/rmR live during the search?

Parameters are copied into each call, so a child spending budget can’t affect its sibling, with no undo needed. (Members also work if you decrement before the call and increment after, just like path. But parameters are harder to get wrong.)

6. Back to 301

Your 301 dfs is the warm-up plus the rules from Lesson 1. Here is what changes:

  1. Signature: void dfs(int i, int open, int rmL, int rmR). The budget travels as parameters, and each child gets the updated copy (see the table below).
  2. Leaf: record path only if open == 0 && rmL == 0 && rmR == 0, and record it into a std::set.
  3. Children: the delete child exists only for a bracket with budget left. The keep child is skipped for a ) when open == 0.
